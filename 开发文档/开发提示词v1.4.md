## 四、本轮 v1.4 总目标

本轮 v1.4 的目标不是做完整商业化 SaaS，也不是一次性实现登录、计费、云部署、GitHub PR、代码沙箱或企业权限系统。

本轮目标是：

1. 把 Agent 路由从关键词匹配升级为 LLM intent classifier，并保留规则兜底。
2. 引入轻量 Workflow 状态机，让 Agent Run 更像真实多 Agent 工作流。
3. 把 Memory 从关键词检索升级为 embedding 语义检索，保留关键词兜底。
4. 把 Skill Registry 从硬编码升级为 YAML / Markdown 配置加载，并支持前端查看、启用、禁用、重新加载。
5. 把 Tool Registry 从硬编码升级为配置加载，并清晰表达风险等级和审批要求。
6. 初步接入 Redis 队列或后台任务机制，让 Agent Run 支持异步状态轮询。
7. 初步接入 MinIO/S3 存储抽象，让文件存储从本地 uploads 过渡到可配置后端。
8. 添加 Playwright E2E 测试，覆盖核心演示流程。
9. 添加 Prompt / Skill / Eval 管理 UI 的基础版本。
10. 添加 Trace 时间线可视化，让 Agent Run 可观察性更强。
11. 添加 Monaco Editor / 代码产物预览能力。
12. 扩展测试和文档，最终生成 `开发报告v1.4.md`。

## 八、任务 1：Agent Intent Classifier

### 8.1 背景

当前 Agent 路由仍偏规则/关键词匹配。v1.4 需要让系统能更准确识别用户意图，并选择合适的 Skill、Workflow 阶段、输出类型和 Eval 维度。

### 8.2 目标

实现一个可测试、可回退的 Intent Classifier。

推荐位置：

```text
apps/api/app/services/intent_classifier.py
apps/api/app/schemas/intent.py
apps/api/app/prompts/intent_classifier.py
apps/api/tests/test_intent_classifier.py
```

### 8.3 分类结果结构

建议返回：

```json
{
  "intent": "prd_generation",
  "selected_skill": "prd-writer",
  "workflow_stage": "product",
  "output_type": "prd",
  "confidence": 0.86,
  "reason": "用户明确要求生成 PRD",
  "requires_documents": false,
  "suggested_next_actions": ["生成 PRD", "补充目标用户", "补充功能边界"]
}
```

至少支持以下 intent：

| intent | selected_skill | workflow_stage | output_type |
|---|---|---|---|
| `competition_analysis` | `competition-analyzer` | `requirement_analysis` | `analysis_report` |
| `idea_generation` | `idea-generator` | `ideation` | `idea_report` |
| `research` | `research-synthesizer` | `research` | `research_report` |
| `prd_generation` | `prd-writer` | `product` | `prd` |
| `architecture_design` | `architecture-designer` | `architecture` | `architecture` |
| `api_design` | `api-designer` | `architecture` | `api_doc` |
| `backend_code` | `fastapi-generator` | `coding` | `backend_code` |
| `frontend_code` | `nextjs-generator` | `coding` | `frontend_code` |
| `qa_debug` | `qa-debugger` | `qa` | `test_report` |
| `pitch` | `pitch-writer` | `pitch` | `pitch` |
| `general_chat` | `context-pack-builder` 或默认 Agent | `general` | `agent_output` |

### 8.4 技术要求

1. 优先使用真实 LLM Provider 分类。
2. 未配置 API Key 时使用规则分类器兜底。
3. LLM 输出必须做 JSON 解析和 schema 校验。
4. LLM 失败时必须降级到规则分类器。
5. 分类结果必须写入 AgentRun 的 metadata 或等价字段。
6. 分类结果必须写入 TraceEvent。
7. 分类结果必须影响 Skill 选择和 Output 类型。
8. 不要为了分类引入昂贵、复杂、不可控的依赖。

### 8.5 前端要求

Agent Chat 页面运行后，应能显示：

```text
识别意图
选择 Skill
Workflow 阶段
置信度
为什么这么选
```

可以放在右侧 Inspector、Run Detail、消息元信息或 Agent Run 卡片中。

### 8.6 验收标准

1. 输入“帮我写一个 PRD”，系统选择 `prd-writer`。
2. 输入“帮我设计数据库和 API”，系统选择架构/API 相关 Skill。
3. 输入“帮我生成答辩稿”，系统选择 `pitch-writer`。
4. 未配置 LLM API Key 时仍能通过规则分类跑通。
5. 分类结果出现在 Trace 中。
6. 相关测试通过。

### 9.2 目标

推荐位置：

```text
apps/api/app/services/workflow_engine.py
apps/api/app/schemas/workflow.py
apps/api/app/models/workflow.py 或复用 agent_runs metadata
apps/api/app/api/v1/workflow.py
apps/api/tests/test_workflow_engine.py
apps/web/app/projects/[projectId]/workflow/
apps/web/components/workflow/
```

### 9.3 默认流程

```text
Start
  ↓
Requirement Analysis Agent
  ↓
Research Agent
  ↓
Product Agent
  ↓
Architecture Agent
  ↓
Coding Agent
  ↓
QA Agent
  ↓

  ↓

  ↓

```

节点状态：

```text

failed
```

### 9.4 后端要求

1. 定义 WorkflowNode / WorkflowEdge / WorkflowRun / WorkflowStep 数据结构。

## 十、任务 3：Memory Embedding 语义检索

### 10.1 背景

v1.3 的 Memory 仍主要依赖关键词匹配。v1.4 需要利用已有 embedding 能力和 pgvector，把 Memory 升级为语义检索。

### 10.2 后端要求

检查现有 Memory 模型。如果没有 embedding 字段，请增加：

```text
embedding Vector(1536) 或与当前 embedding provider 一致的维度
embedding_model
embedding_status
last_embedded_at
```

要求：

1. 新建 Memory 时自动生成 embedding。
2. 更新 Memory 内容时重新生成 embedding。
3. 删除 Memory 时正常清理。
4. 检索时优先走 pgvector similarity search。
5. 如果 embedding 不存在或数据库不支持 pgvector，则降级到关键词检索。
6. 检索结果应包含 score / distance / match_type。
7. Context Pack 中要标明 Memory 来源和 score。
8. 相关 Tool Call 记录应从 `memory_search` 输出命中数量和 score。
9. 增加 Alembic migration。

### 10.3 API 建议

```text
GET  /api/v1/projects/{project_id}/memory/search?q=xxx&mode=semantic
POST /api/v1/projects/{project_id}/memory/{memory_id}/reembed
POST /api/v1/projects/{project_id}/memory/reembed-all
```

### 10.4 前端要求

Memory 页面增加：

1. 搜索框支持 semantic / keyword 模式切换。
2. Memory 卡片显示 embedding 状态。
3. 搜索结果显示相似度或匹配方式。
4. 提供单条重新嵌入按钮。
5. 提供全部重新嵌入按钮；如果成本较高，应弹确认。
6. 如果未配置 LLM/Embedding Key，要明确显示当前处于 Mock Embedding 或降级模式。

### 10.5 验收标准

1. 新建 Memory 后生成 embedding。
2. 搜索同义表达能命中相关 Memory。
3. Agent Run 构建 Context Pack 时使用语义 Memory。
4. Trace 和 Tool Call 中能看到 memory_search。
5. 未配置 API Key 时系统仍可运行。

## 十一、任务 4：Skill Registry 配置化

### 11.1 背景

v1.3 的 Skill Registry 仍偏硬编码。总体架构希望 Skill 能从 `skills/*/SKILL.md` 或 YAML 定义加载。

### 11.2 目标

实现配置化 Skill Registry，使 Skill 定义可维护、可重新加载、可展示。

推荐目录结构：

```text
skills/
  prd-writer/
    skill.yaml
    SKILL.md
    examples/
    templates/
  architecture-designer/
    skill.yaml
    SKILL.md
    examples/
    templates/
```

### 11.3 skill.yaml 建议字段

```yaml
name: prd-writer
display_name: PRD Writer
version: 1.0.0
category: product
description: Generate structured PRD for innovation projects.
enabled: true
inputs:
  - project_goal
  - context_pack
outputs:
  - prd
required_tools:
  - rag_search
  - memory_search
risk_level: low
prompt_template: templates/default.md
eval_rubric: evals/rubrics/prd.yaml
```

### 11.4 后端要求

1. 启动时扫描 `skills/` 目录。
2. 解析 `skill.yaml` 和 `SKILL.md`。
3. 校验字段，缺失字段给出清晰错误。
4. 将 Skill 定义同步到数据库或缓存。
5. `GET /skills` 返回配置加载结果，而不是纯硬编码。
6. `POST /skills/reload` 重新加载配置。
7. `PATCH /skills/{skill_name}` 支持启用/禁用，状态持久化。
8. 如果配置文件损坏，不能导致整个后端崩溃，应标记为 invalid 并显示错误。

## 十三、任务 6：Redis 异步 Agent Run 与状态轮询

### 13.1 背景

Redis 已配置但未实际使用。Agent Run 如果同步执行，后续复杂工作流会阻塞请求。v1.4 需要引入轻量异步机制。

### 13.2 可选方案

优先采用低复杂度方案：

方案 A：FastAPI BackgroundTasks + Redis 状态缓存。  
方案 B：RQ / Dramatiq / Celery。  
方案 C：暂不引入 Worker 进程，只建立抽象层和状态轮询。

如果时间有限，选择方案 A 或 C。不要为了异步队列引入过重复杂度导致项目不可启动。

### 13.3 后端要求

1. Agent Run API 支持 `async=true`。
2. 异步模式下立即返回 `run_id` 和 `status=queued`。
3. 后台执行时更新状态：queued → running → success/failed。
4. 提供状态查询 API：

```text
GET /api/v1/projects/{project_id}/agents/runs/{run_id}
```

5. 如果 Redis 不可用，降级为数据库轮询或同步执行，并在 `/health` 中说明。
6. 失败信息要写入 AgentRun、TraceEvent、日志。

### 13.4 前端要求

1. Chat 页面发送后显示 queued / running 状态。
2. 前端轮询 run status，直到 success/failed。
3. 运行中禁用重复提交或显示“正在运行”。
4. 成功后自动显示输出、Eval、Tool Calls。
5. 失败后显示错误和 Trace 入口。

### 13.5 验收标准

1. Agent Run 能以异步方式提交。
2. 页面能看到状态变化。
3. 后端重启或失败时有清晰错误。
4. Redis 不可用时项目仍能运行。
